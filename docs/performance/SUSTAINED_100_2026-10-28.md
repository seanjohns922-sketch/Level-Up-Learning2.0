## Scope and mixed-load phases

The background protocol run targets 100 distinct synthetic students, four ordinary
teachers, 20,000 base historical events and 1,800 seconds. Students issue presence
and active-time writes every 30 seconds; teachers request complete paged event
snapshots every two seconds. The final check reads back each student's exact
active-time increment. All traffic targets the loopback-only Supabase environment.
This is not a production/cloud load test or browser/iPad rendering test.

A separate two-minute, four-teacher test mirrored all six LiveClassPanel read
sources during the background run: current activity, paged events, lessons,
weekly quizzes, assessments and today's activity. It passed 220 snapshots / 3,744
HTTP requests, with snapshot p95 223 ms, p99 418 ms and no errors. Attempt reads
verified canonical evidence for every fixture student. Their much larger historical
volumes and API caps remain a separate test requirement.

Completion/retry/realtime bursts were then run during background traffic. They
modify question/XP counters but add zero active-time seconds, so they do not
invalidate the background test's exact seconds-delta assertions. This verified
exception to the usual one-workload-per-fixture rule applies only to these known
operations; arbitrary concurrent fixture runs remain unsafe for integrity checks.

## Local gateway limit found and corrected

The initial completion burst verified only 85/100 journeys and received 82/100
teacher events. A diagnostic repeat verified 98/100 journeys, with two
`UND_ERR_SOCKET` failures on assessment reads. The test remained failed; no retry
was added and no integrity/latency gate was relaxed. The harness now records
transport failures explicitly instead of omitting them from endpoint counts.

The local Kong gateway logged `512 worker_connections are not enough, reusing
connections` at the same times. Its Nginx config had one worker and no explicit
worker_connections setting; the process file-descriptor limit was 1,048,576.
No database crash was found in the inspected logs, and containers stayed healthy.

At 04:25:14 UTC the **local-only** gateway was changed to 4,096 worker connections,
its configuration was validated, and Nginx was gracefully reloaded. The original
configuration was retained inside the container. No production gateway settings,
application permissions or student database schema changed.

Two identical bursts after that change each passed all 100 journeys, 2,200 expected
student RPC requests, 600 explicit missing/cross-student denial checks, all teacher
canonical-score reads and all 100 realtime events. Maximum observed realtime
latency was 1,035 ms and 952 ms respectively. No new connection-exhaustion warning
was observed in the checked post-change interval. These results support the local
gateway diagnosis; they do not establish a managed-cloud gateway limit.

**The environment changed partway through this run.** Preserve the original
failures and report the background outcome separately. Do not describe this as a
clean, unchanged-configuration acceptance test. A clean repeat should start with
the intended gateway setting already applied.

## Reproduction and monitoring

```sh
node scripts/staging/tune-local-gateway.mjs
# Run in separate terminals; the monitor records aggregates only.
SCALE_MONITOR_SECONDS=1800 node scripts/staging/monitor-local.mjs
SCALE_DURATION_SECONDS=1800 node --experimental-strip-types scripts/staging/capacity-local.mjs
# Optional read-only dashboard burst while the background run is active:
node --experimental-strip-types scripts/staging/dashboard-snapshot-local.mjs
```

The tuning script targets only `supabase_kong_reliq-scale-local`, checks the local
API configuration, preserves `nginx.conf.capacity-backup`, validates before reload,
and is idempotent at 4,096. Use `--restore` to restore that backup. Supabase CLI
container recreation may regenerate the default config, so recheck before a run.
The monitor samples container CPU/memory/network/block I/O and aggregate database
connection counts approximately every 30 seconds. These are point samples, not
continuous maxima or production headroom measurements.

Future runs write `capacity-progress.json` every 30 seconds with elapsed time,
operation counts and completed integrity checks. This instrumentation was added
after the current process started; the current run uses its final result plus the
independent resource monitor. Test fixtures and local sessions remain isolated.

The app/data-path tests and their role/score gates are unchanged. No production
application build is required for these test-only script/document changes. The
10,000-user claim, production-equivalent cloud resources, representative browsers,
larger historical datasets and the deferred security audit remain outstanding.

## Background result and stricter presence checks

The original 1,800-second background run **failed overall**. It verified all 6,000
active-time increments, but one teacher snapshot journey failed with
`UND_ERR_SOCKET` and stopped early. Its raw result is retained in
`soak-background-original-2026-10-28.json`. The older HTTP-status-only failed-count
field showed zero because the composite reader returned a page error alongside
the initial successful response status; the nonempty failure list and false gate
are authoritative. The harness now counts an error-bearing snapshot as failed
regardless of its inherited status. Do not describe this run as four teachers
successfully refreshing for the entire 30 minutes.

A direct fixture check also found no live-activity rows for the students.
`touch_live_student_presence_secure` legitimately returns false when there is no
row to update. Older fixture/smoke/load checks accepted HTTP 200 without checking
that boolean, so their presence calls did not establish persisted heartbeats.
This was a coverage defect in the test harness, not evidence of an application
write failure. The initial six-source dashboard run likewise did not establish
nonempty current-activity coverage.

The seeder, smoke and capacity runner now initialise activity through the actual
student-session `upsert_live_student_activity_secure` endpoint and require every
touch to return true. The capacity runner reads every student's activity row back
and requires a recent persisted heartbeat. Full-dashboard checks now require live
activity evidence for all 25 students in each fixture class, preventing vacuous
success on an empty table. No production auth, data or application code changed.

After these corrections and with the gateway at 4,096 from the start, a 120-second
run passed: 100/100 persisted presence checks, all 400 active-time increments,
zero failed operations and complete event snapshots. It recorded 1,632 logical
operations (1,404 student/login HTTP requests plus 228 snapshots); the snapshots
used 2,565 HTTP requests. Login p95 was 336 ms, actual heartbeat update p95 107 ms,
activity write p95 71 ms and complete event snapshot p95 273 ms. See
`soak-corrected-short-run-2026-10-28.json`.

The independent monitor recorded 56 samples over 29 minutes, without sampling
errors. The largest sampled database connection count was 36. Database CPU's
largest observed Docker sample was 87.39% (Docker's CPU measure, not a whole-host
capacity certificate); database memory was 219.9 MiB in the first sample and
260 MiB in the last. Current monitor code also includes the gateway for future
runs; the retained current-run samples include database, REST and realtime only.
